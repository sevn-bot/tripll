Architecture

How tripll turns wave-plan files into a RunGraph and executes it with worktree isolation, human gates, retries, and integration.

The RunGraph

A plan set is parsed into a RunGraph of waves. Each wave has dependencies, an optional review gate, owned paths, and verify targets. The graph is layered into batches that run in order; waves within a batch can run in parallel.

  • Lanes — independent streams of work, isolated by owned paths.
  • Batches — dependency layers executed sequentially.
  • Pre-0 gate — a human approval stop derived from ## Wave W0 sections and decision rows marked for W0.
  • CW seams — content-window hotspots forbidden to lanes that do not own them.

Execution engine

The engine dispatches each wave to a backend adapter inside a dedicated git worktree, enforces owned-path scope (reverting out-of-scope changes), runs verify commands, retries failures up to a limit, and escalates when exhausted. Batches can be integrated onto a single branch.

Tests-first model

An optional role column drives a tests-first flow: W0 (gate) → W1 test-creator (full RED suite) → impl waves (green) → Final. W1 is the single owner of tests/; implementation waves are forbidden from editing tests and get extra attempts before escalation.

State & observability

Run state is tracked in a SQLite ledger with an atomic state machine. Logs go through loguru; optional Logfire/OpenTelemetry tracing is enabled by the obs extra and is a no-op without LOGFIRE_TOKEN.
